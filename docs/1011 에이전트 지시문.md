# 에이전트 지시문: 1단계 마무리 (2026-10-11 기준)

Claude Code나 Codex에 그대로 붙여 넣는 작업 지시문 모음입니다. 지시문 번호는 [`1011 작업 정리.md`](1011%20작업%20정리.md) 2절의 작업 번호와 같습니다. 작업 1은 직접 하는 일이라 지시문이 없습니다.

## 사용법

- **로컬 에이전트 전용:** Claude Code, Codex CLI처럼 이 Mac의 프로젝트 폴더에서 실행하는 에이전트에 맡기세요. 검증 도구가 이 Mac에 설치된 Unity의 컴파일러를 쓰기 때문에, 클라우드에서 도는 에이전트에서는 검증이 동작하지 않습니다.
- **복사 방법:** 각 지시문의 코드 블록 전체를 복사해서 붙여 넣으세요. `【 】` 안은 직접 채우는 칸입니다.
- **0절:** 모든 지시문이 첫 줄에서 에이전트에게 이 파일의 0절(공통 규칙)을 읽게 합니다. Codex는 `CLAUDE.md`를 자동으로 읽지 않지만, 0절이 읽도록 지시합니다.
- **대화 단위:** 한 대화에 작업 하나씩 맡기세요. 다음 작업은 새 대화에서 시작하는 것이 깔끔합니다.
- **끝난 뒤:** 에이전트의 보고를 읽고, Unity 창을 한 번 클릭하세요. Unity는 창이 활성화될 때 다시 컴파일합니다. 그다음 보고에 적힌 확인 항목을 직접 확인합니다.

## 0. 공통 규칙 (에이전트가 읽는 부분)

당신은 Unity 6000.3 모바일 퍼즐 게임 **Cameli Garden**(Android·iOS, 세로 화면) 개발을 돕습니다. 사용자는 한국어를 씁니다. 보고와 질문은 한국어로 하세요.

### 0.1 작업 전에 읽을 것
1. `CLAUDE.md` 전체: 빌드·검증 방법과 코드 구조
2. `docs/Cameli Garden.md`: 기획서이자 게임 규칙의 기준입니다. 특히 3절(핵심 규칙), 4절(기믹), 11~13절(로드맵, 합격 기준, 미정 항목)을 읽으세요.
3. `docs/1011 작업 정리.md`: 진행 상황과 작업 목록. 더 최근 날짜의 `docs/MMDD 작업 정리.md`가 있으면 그것도 읽으세요.
4. 이 파일에서 **지시받은 작업만** 하세요. 다른 작업의 지시문은 참고만 합니다.

### 0.2 코드 구조에서 지킬 것
- **규칙은 `Assets/Scripts/Cameli/Core/`에만 둡니다.** 이 폴더는 어셈블리 `Cameli.Core`이고, `noEngineReferences`라서 `UnityEngine`을 참조하면 안 됩니다.
  - 이동 규칙은 `Rules.Step` 한 곳에만 있습니다. 게임(`GameSession`), 솔버(`Solver`), 검증 도구(`Tools/CameliHarness/LevelLab.cs`)가 모두 이 함수를 씁니다. 규칙을 다른 곳에 복제하지 마세요.
  - netstandard 2.1 + C# 9로 컴파일됩니다. `record`와 `init` 접근자는 netstandard 2.1에서 컴파일되지 않으니 쓰지 마세요.
- **게임 화면은 `Assets/Scripts/Cameli/Game/`입니다** (Assembly-CSharp, namespace `Cameli.Game`). `CameliGame`이 uGUI 전체를 코드로 만들며, 프리팹과 씬 연결이 없습니다.
- 에디터 메뉴는 `Assets/Scripts/Editor/Cameli/CameliMenu.cs`에 있습니다.
- 테스트는 `Assets/Tests/EditMode/Cameli/`에 있습니다.
  - `CoreTests.cs`: Editor 밖에서도 실행됩니다.
  - `StageFileTests.cs`: Unity Test Runner에서만 실행됩니다.
- 스테이지는 `Assets/Resources/CameliStages/stage_NN.json`입니다. 형식은 `CLAUDE.md`의 "Stage files"를 보세요.
- **기존 프로토타입 코드는 건드리지 마세요:** `Assets/Scripts/` 아래 Cameli 폴더 밖의 GameManager, GridManager, PlayerController, Dashboard 등
- 입력은 Input System(`Keyboard.current`, `InputSystemUIInputModule`)을 씁니다. 레거시 `Input.GetKeyDown`을 새로 쓰지 마세요.
- UI 문구와 코드 주석은 한국어로 씁니다. 이름 짓기와 주석 양은 주변 코드에 맞추세요.

### 0.3 Unity 파일 주의
- `.cs` 파일을 옮기거나 이름을 바꿀 때는 `.meta` 파일도 함께 옮기세요.
- 새 파일의 `.meta`는 직접 만들지 마세요. Unity가 불러올 때 만듭니다.
- **씬은 항상 새로 만들어서 작업합니다.** 기존 씬(`Assets/0. Scenes/Puzzle.unity`, `Old_Puzzle.unity`)은 열어서 고치거나 다시 저장하지 마세요. 새 씬이 필요하면 `CameliMenu.cs`에 씬을 만드는 메뉴를 추가하세요. "Cameli → 프로토타입 씬 만들기"가 `Prototype.unity`를 새로 만드는 방식과 같습니다.
- 씬(`.unity`), 프리팹, `ProjectSettings/*.asset` 같은 Unity YAML 파일은 손으로 편집하지 마세요. 설정을 바꿔야 하면 `CameliMenu.cs`에 메뉴 코드를 추가하고, 사용자에게 메뉴 실행을 요청하세요.
- Unity batchmode는 실행하지 마세요. Editor가 보통 열려 있어서 실패합니다.

### 0.4 검증 (완료라고 보고하기 전에 반드시)

프로젝트 루트에서 순서대로 실행합니다.

```bash
Tools/CameliHarness/test-core.sh      # 규칙 코어 테스트 (Editor 밖)
Tools/CameliHarness/check-unity.sh    # Unity 스크립트 3개 어셈블리 컴파일 검사
Tools/CameliHarness/lab.sh check      # 모든 스테이지 검증 (풀이 가능, 최단 걸음 일치, 방울 수, 게이트 사용)
```

- **세 개 모두 통과해야 완료입니다.** 실패하면 고치세요. 고치지 못하면 출력을 그대로 보고하세요.
- 시스템 `dotnet`은 없습니다. 스크립트는 Unity에 내장된 컴파일러와 런타임을 씁니다. `dotnet test`는 쓰지 마세요.
- Unity Editor의 컴파일 오류는 `~/Library/Logs/Unity/Editor.log`에서 `error CS`로 찾을 수 있습니다. 다만 Editor는 창이 활성화되어야 다시 컴파일하므로, 로그가 최신이 아닐 수 있습니다. 로그의 시각을 확인하세요.
- `StageFileTests`처럼 Unity Test Runner에서만 도는 테스트는, 사용자에게 실행을 요청하세요.

### 0.5 Git
- 브랜치 `phase1-prototype`에서 작업합니다. 브랜치 전환, `main` 병합, push는 지시가 있을 때만 합니다.
- 커밋은 지시문에 "커밋" 항목이 있을 때만 합니다.
- `git add -A`와 `git add .`는 쓰지 말고, 파일을 지정해서 추가하세요.
- 다음은 절대 커밋하지 마세요: `.DS_Store`, `.vscode/`, `*.slnx`, `Tools/CameliHarness/out/`, `Library/`, `Temp/`, `Logs/`, `UserSettings/`, 빌드 결과물(`*.apk`, Xcode 프로젝트 폴더)
- 새 에셋은 `.meta`와 함께 커밋합니다. `.meta`가 없으면 커밋하지 말고, 사용자에게 Unity 창을 한 번 클릭해 달라고 요청하세요.
- 커밋 메시지는 영어로, 한 줄 요약과 필요하면 본문을 씁니다.

### 0.6 기획과 범위
- 구현하다가 기획서의 확정 결정과 달라야 할 것 같으면, **멈추고 질문하세요.**
- 지시문에 없는 기능은 추가하지 마세요. 개선 아이디어는 보고의 "제안"에 적으세요.

### 0.7 문서

- 한 일은 **오늘 날짜**의 `docs/MMDD 작업 정리.md`에 짧게 기록하세요(MMDD는 월일 네 자리, 예: `1015`). 파일이 없으면 `1011 작업 정리.md`의 형식(한 일 요약, 상세, 남은 일)으로 새로 만드세요.
- 명령, 구조, 규칙이 바뀌면 `CLAUDE.md`도 고치세요. 이 파일은 영어로 되어 있습니다.

  - 기획서 3.2에 적으세요: 배수 레시피도 클리어로 인정한다. 대신 스테이지는 최단 정답의 방울 수가 목표 방울 수와 같은 것만 쓴다(`lab.sh check`의 Exact 조건). 게이트도 같다(GatesPassedExactly 조건).
(b) 방울 수까지 정확히 맞아야 클리어
  - 클리어 조건 = 색 일치(±2) 그리고 방울 합계가 목표 레시피의 방울 합계와 같음. 플레이어가 화면에 보이는 정보(색, "방울 x/y")만으로 판단할 수 있게 하려는 것입니다.
  - `Rules.Step`의 클리어 판정에 `drops.Total == stage.Target.Total`을 추가하세요.
  - 게이트도 같은 규칙입니다. `Rules.CanPassGate`에 방울 합계가 `gate.Recipe.Total`과 같아야 한다는 조건을 추가하세요.
  - 막다른 상태 안내
    - 판정: 현재 방울 합계가 목표와 모든 게이트 레시피의 방울 합계보다 크면, 이번 판에서는 더 이상 클리어도 문 통과도 할 수 없습니다.
    - Core에 판정 함수를 두세요(예: `Rules.IsOverfilled(stage, state)`).
    - 이 상태가 되면 HUD 메시지로 "방울이 너무 많아요. 되돌리기나 처음부터를 눌러 보세요."를 보여 주세요.
    - HUD의 "방울 x/y"는 x > y일 때 `Theme.Accent` 색으로 강조하세요.
  - `Solver`: 방울 합계가 (목표와 게이트 레시피 합계 중 최댓값)을 넘는 상태는 탐색하지 않게 하세요. 기본 `maxDrops`를 그 값으로 바꾸면 됩니다.
  - `LevelLab`의 Exact와 GatesPassedExactly 조건은 이제 규칙이 보장합니다. 지우지 말고 남겨 두세요. 항상 통과해야 정상입니다.
  - 테스트 (`CoreTests.cs`)
    - 비율이 같은 배수(목표 RB에 R2B2)로는 클리어되지 않음
    - 정확한 방울 수면 클리어됨
    - 게이트를 배수로는 통과하지 못함
    - 막다른 상태 판정 함수
  - 기획서 3.2, 3.3, 4.2를 고치세요. 클리어는 "목표색이 되고 방울 수가 목표와 같아지는 순간"이고, 게이트도 같은 기준입니다.

[B. 게이트 통과 방식]
(a) 문 칸에 멈춰 섬 (지금 동작)
  - 코드는 바꾸지 않습니다.
  - 기획서 4.2에 적으세요: 플레이어는 문 칸에 멈춰 선다. 같은 쪽으로 되돌아 나오면 색이 빈 채로 돌아가며, 이는 의도된 동작이다. 스테이지는 최단 정답이 문 너머에서 끝나는 것만 쓴다(`lab.sh check`의 BeyondGate 조건).
(b) 문을 지나 반대편 칸까지 한 번에
  - `Rules.Step`: 이동 방향의 칸이 게이트이고 통과 조건을 만족하면, 그 너머 칸(게이트에서 같은 방향으로 한 칸 더)을 봅니다.
    - 너머 칸이 판 밖, 벽, 또는 다른 게이트이면 막힙니다. 상태는 바뀌지 않습니다. 결과는 `BlockedByGate`와 구분되는 새 값으로 돌려주세요(예: `BlockedBeyondGate`).
    - 그 밖의 경우: 색을 비우고(소모형 게이트) 너머 칸에 도착합니다. 너머 칸이 아직 안 먹은 색 칸이면, 빈 색에 그 색 한 방울을 먹습니다. 그 결과로 클리어 판정도 합니다(결정 A의 규칙대로).
    - 걸음 수는 1 늘어납니다. 스와이프 한 번 = 1걸음입니다.
    - 플레이어가 게이트 칸에 서 있는 상태는 더 이상 생기지 않아야 합니다.
  - `MoveOutcome`
    - 게이트를 지난 뒤 먹었는지, 클리어했는지 화면이 알 수 있게 설계하세요. 예: `PassedGate` + 이전·다음 상태 비교, 또는 별도 플래그
    - `IsMove()`는 enum 순서(`outcome <= Cleared`)에 의존합니다. 새 값을 넣을 때 순서를 확인하세요.
  - 되돌리기 1회로 게이트 통과 전체가 취소되어야 합니다. `GameSession`은 상태 스냅샷 스택이라 그대로 맞을 것입니다. 테스트로 확인하세요.
  - `BoardView`: 두 칸 거리를 게이트 칸을 지나 직선으로 이동하는 애니메이션. 시간은 한 칸의 두 배이고, 입력 버퍼 동작은 유지합니다.
  - `CameliGame` 메시지: 너머로 갈 수 없을 때 "문 너머로 갈 수 없어요."를 보여 주고 흔들기
  - 스테이지 검증(`StageDefinition.FromFile`)
    - 각 게이트는 상하 또는 좌우 중 한 축에서, 양쪽 이웃이 모두 걸을 수 있는 칸이어야 합니다(판 안, 벽이나 게이트가 아님).
    - 아니면 `StageFormatException`을 던지고, 테스트를 추가하세요.
  - 스테이지 10~13
    - 최단 걸음이 바뀝니다. `lab.sh check`로 새 값을 확인하고, 각 json의 `optimalMoves`를 고치세요.
    - 다른 조건(게이트가 필요함, 정확한 방울 수, 정답 조합 수)이 깨진 스테이지가 있을 때:
      - 칸 1~2개만 바꿔 같은 의도를 유지할 수 있으면 고치고, 바뀐 내용을 보고하세요.
      - 더 크게 바꿔야 하면 `lab.sh search`로 후보를 찾아 제시만 하고 멈추세요.
  - `LevelLab`
    - BeyondGate 조건은 남겨 두세요.
    - `lab.sh solve` 출력이 두 칸 이동을 제대로 보여 주는지 확인하세요.
  - 테스트
    - 통과 후 너머 칸 도착과 먹기
    - 너머가 벽이거나 판 밖이면 막힘
    - 되돌리기가 통과 전체를 취소함
    - 솔버 경로 어디에도 게이트 칸 위치가 없음
  - 기획서 4.2를 고치세요.

[C. 재시작 시 되돌리기]
(a) 다시 채움 (지금 동작)
  - 코드는 바꾸지 않습니다. 기획서 3.4에 "재시작하면 되돌리기도 3회로 다시 채워진다"를 적으세요.
(b) 스테이지에 새로 들어올 때만 채움
  - `GameSession.Restart()`가 `UndosRemaining`을 유지하게 하고, 생성자에서만 채우세요.
  - `CameliGame`이 스테이지를 바꿀 때 새 `GameSession`을 만드는지 확인하세요. 그래야 그때 다시 채워집니다.
  - 테스트와 `GameSession`의 주석을 고치고, 기획서 3.4에 적으세요.

마무리:
